# 2026-11-02

## 오늘 한 것
- 회원 생성 흐름에서 Controller, Service, Domain의 책임을 학습
- HTTP 요청 DTO와 Service 입력 Command를 분리
- Service가 Member를 반환하고 Controller가 응답 DTO를 구성하도록 흐름 정리
- 학습 내용을 기억에서 꺼내 설명하며 복습
- Spring Data JPA와 PostgreSQL로 회원 저장·조회 흐름 연결
- Member 조회 API와 MemberNotFoundException, 전역 404 오류 응답 처리 추가
- ApiResponse 오류 응답의 제네릭 타입을 `Void`로 명시
- 사용자가 직접 DB 저장, 회원 조회, 존재하지 않는 ID의 404 JSON 응답을 확인

## 학습한 내용
- Controller는 HTTP 요청과 응답을 다룬다.
- Service는 유스케이스의 흐름을 조율하고, Member는 자신의 상태와 생성 규칙을 관리한다.
- `MemberCreateRequest`는 HTTP JSON 입력을 표현한다.
- `CreateMemberCommand`는 회원 생성 유스케이스에 필요한 입력을 전달한다. 두 입력은 지금 필드가 같지만 변경 이유와 경계가 다르다.
- Service가 HTTP 응답 DTO를 만들지 않고 Member를 반환하면, HTTP 응답 표현을 Controller에 둘 수 있다.
- Spring Data Repository가 저장 및 조회 메서드 구현을 제공하며, Service가 이를 호출해 유스케이스 흐름을 조율한다.
- 조회 결과가 없으면 Service가 `MemberNotFoundException`을 던지고 전역 예외 처리기가 이를 404 응답으로 변환한다.
- `ApiResponse<Void>`는 오류 응답에 data가 없음을 타입으로 나타낸다. raw type은 현재 응답을 깨뜨린 버그라기보다 타입 검사가 약해지는 문제였다.
- 로컬 학습에서 스키마 변경이 잦아 `ddl-auto: create-drop`을 사용한다. 애플리케이션 재시작 시 테이블과 실습 데이터가 초기화되는 것을 의도한다.
- 비밀번호는 현재 평문으로 저장되므로 실제 계정 정보를 사용하지 않는다. 해싱은 인증·보안 학습 단계에서 원리부터 다루기로 했다.

## 실제 동작 확인
- 사용자가 회원 생성 요청 후 PostgreSQL에 데이터가 저장되는 것을 확인
- 조회 API로 저장된 회원을 가져오는 것을 확인
- 존재하지 않는 ID 조회 시 HTTP 404와 오류 JSON 응답을 확인
- 자동 테스트는 실행하지 않음
